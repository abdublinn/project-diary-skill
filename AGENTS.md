# AGENTS.md — Дневник проекта (вариант для Codex / агентов на AGENTS.md)

> Это нативная для Codex версия скила `project-diary`. У Codex нет понятий
> «скил» и «SessionStart-хук» — механизмом «всегда в контексте» служит сам
> `AGENTS.md`. Поэтому правило ниже написано как прямая инструкция агенту.
>
> **Куда положить:**
> - на все проекты сразу — добавь блок «=== ДНЕВНИК ПРОЕКТА ===» ниже в свой
>   глобальный `~/.codex/AGENTS.md`;
> - на один проект — в `AGENTS.md` в корне этого проекта.
>
> Блок самодостаточный: копируется целиком, ничего внешнего не требует.

=== ДНЕВНИК ПРОЕКТА ===

## Что это и зачем

В корне проекта живёт файл `ДНЕВНИК.md` — короткий журнал передачи смены между
сессиями. Он решает ровно две задачи:

1. **Передача смены.** Новая сессия за минуту понимает: где проект сейчас, что
   сделано, какие решения приняты и почему, на чём остановились, куда дальше,
   где грабли.
2. **Обзор для владельца.** Человек открывает один файл и видит общую картину
   без чтения кода, коммитов и переписки.

Дневник **не** архив, **не** лог действий, **не** дубликат `git log`. Если
запись не служит одной из двух задач — её там быть не должно.

## В начале работы над проектом — ПРОЧИТАЙ

Первым делом найди `ДНЕВНИК.md`: в текущей рабочей директории, иначе — поднимаясь
вверх по дереву до ближайшей папки-маркера проекта (`.git`, `package.json`,
`pyproject.toml`, `.obsidian` и т.п.). Если нашёл — прочитай блок «Снимок»
(обычно этого достаточно), при необходимости последние записи «Журнала», и
только потом действуй. Не пересказывай дневник без запроса — просто учитывай.

Если файла нет, а работа над проектом нетривиальная и продолжительная — заведи
его (см. «Создание дневника»). Для разовых мелких задач дневник не нужен.

## По ходу работы — ВЕДИ

Пиши не после каждой правки, а на **веху**:

- завершена осмысленная задача или её крупный этап;
- принято нетривиальное решение с альтернативой (фиксируй с обоснованием);
- возник блокер / важный открытый вопрос;
- конец сессии / передача контекста дальше.

На каждой вехе: перезапиши блок «Снимок» и добавь одну запись в «Журнал» сверху.

**Перед сжатием контекста — не жди.** У Codex нет хука, который напомнит, —
следи сам: если контекст подходит к пределу, диалог стал длинным или сессия
скоро прервётся, а веха/решение ещё не записаны — обнови `ДНЕВНИК.md`
заблаговременно, пока наработанное в контексте. Потеря состояния при сжатии —
главный риск передачи смены.

## Структура `ДНЕВНИК.md`

Три блока, роли не смешивать:

- **📍 Снимок** — живое состояние, ПЕРЕЗАПИСЫВАЕТСЯ (не растёт, прошлое уходит в
  «Журнал»). Заголовок несёт штамп свежести `Обновлено: <ГГГГ-ММ-ДД>` и, если
  проект под git, ` · <короткий-sha>` — холодная сессия сразу видит, отстал
  снимок или нет. Поля: **Следующий шаг (сразу делать)** — ОДНА копируемая
  строка, конкретное действие прямо сейчас (самое ценное поле); Фаза/цель
  сейчас; На чём остановились; Дальше по плану (1–3); Открытые вопросы/блокеры;
  Осторожно/грабли.
- **🧭 Ориентир** — полустатичный: Что это (1–2 фразы); Точки входа
  (файлы/папки/команды); Как проверить. Меняется редко.
- **📒 Журнал** — append-only, новое сверху. Запись = одна веха: Сделано
  (результат, не процесс); Решение … — **почему** … (только если был выбор);
  Состояние после; Дальше. Записи не редактируются и не удаляются.
  **Потолок (детерминированный):** полные записи для ≈12 последних вех ИЛИ пока
  «Журнал» ≤ ≈150 строк — что раньше; переполнение сворачивай по одной строке в
  `### Архив (свёрнуто, новое сверху)` в том же файле. Отдельных архивных файлов
  не плодим — однофайловость важнее «полноты».

Формат: обычный код-репозиторий → плоский Markdown. Проект внутри
Obsidian-vault (есть `.obsidian/` среди родителей) → Obsidian Flavored Markdown
(frontmatter + callouts).

### Шаблон (плоский Markdown)

```markdown
# Дневник проекта — <Название>

> Назначение: ввести новую сессию в курс дела и дать владельцу обзор.
> Не лог действий — только вехи, решения, состояние.

## 📍 Снимок · Обновлено: <ГГГГ-ММ-ДД>[ · <git-sha>]
- **Следующий шаг (сразу делать):** … (одна копируемая строка)
- **Фаза / цель сейчас:** …
- **На чём остановились:** …
- **Дальше по плану:** 1) … 2) …
- **Открытые вопросы / блокеры:** …
- **Осторожно / грабли:** …

## 🧭 Ориентир по проекту
- **Что это:** …
- **Точки входа:** …
- **Как проверить:** …

## 📒 Журнал (новое сверху)

### <ГГГГ-ММ-ДД> — <короткий заголовок вехи>
- **Сделано:** …
- **Решение:** … — **почему:** …
- **Состояние после:** …
- **Дальше:** …

### Архив (свёрнуто, новое сверху)
- <ГГГГ-ММ-ДД> — <заголовок древней вехи>
```

## Что НЕ писать (против мусора) — это ядро

- Не лог инструментов и шагов («прочитал X, запустил Y») — пиши итог и
  состояние, а не трассу.
- Не пересказывай код и git-историю — дай указатель, не копию.
- Решение без «почему» не писать.
- Одна запись на веху, не на правку.
- «Снимок» не растёт — он перезаписывается.
- «Журнал» не растёт бесконечно — соблюдай потолок (≈12 вех / ≈150 строк),
  старое сворачивай в `### Архив`.
- Не дублируй другие постоянные заметки агента (`AGENTS.md`, память) — про
  пользователя/межпроектное туда, в дневник максимум короткая ссылка.
- Без воды и самоотчётов. Телеграфный стиль, факты.

Перед сохранением по каждой строке спроси: «помогает новой сессии войти в курс
ИЛИ даёт владельцу обзор?» Нет — удали строку.

## Создание дневника, если его нет

1. Определи корень проекта и формат.
2. Реконструируй *текущее* состояние из `git log`, README, структуры папок,
   текущего разговора. Прошлое, которого не знаешь, не выдумывай.
3. Создай файл по шаблону; в «Журнал» — одна честная стартовая запись:
   «Дневник заведён (реконструкция состояния)».
4. Коротко сообщи пользователю, что дневник заведён.
